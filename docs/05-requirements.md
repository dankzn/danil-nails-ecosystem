# Requirements

Дата фиксации: 2026-09-24.

## Бренд и запуск

- Публичное название: Danil Nails Studio.
- Стартовая модель: один мастер, владелец одновременно является мастером и суперпользователем.
- Будущая модель: салон с несколькими мастерами и администраторами.
- Стартовый город: Москва.
- Будущая география: Испания.
- Языки: русский, английский, испанский.
- Первый запуск: закрытый тест для владельца. После успешного теста ссылка дается клиентам для записи.
- GitHub-репозиторий пока публичный. Позже его можно закрыть.

## Каналы и приоритеты

- В первом запуске важны CRM, запись клиента и Telegram.
- WhatsApp Business уже есть, но WhatsApp не обязателен для первого запуска.
- Telegram bot создается через BotFather, код бота пишется с нуля.
- WhatsApp и онлайн-эквайринг проектируются как будущие интеграции.
- Хостинг на старте должен быть максимально бесплатным и с аккуратной ссылкой. Перед деплоем нужно отдельно проверить актуальные бесплатные тарифы.
- До отдельного прямого решения owner вся инфраструктура должна работать на тарифах стоимостью `0 ₽`: без обязательной банковской карты, автоматических списаний и платных дополнений.
- CRM, API и публичный сайт размещаются отдельными проектами на Vercel; база данных остаётся в Supabase.
- Целевое бесплатное размещение CRM и API должно исключать многосекундное пробуждение сервера. До отдельного решения владельца нельзя подключать платный тариф или банковскую карту.

## Быстродействие CRM

- Нажатие навигационной кнопки или открытие карточки должно давать видимый результат сразу, без блокировки всего интерфейса ожиданием сети.
- Повторно открываемые данные можно кэшировать в пределах сессии, но после изменения записи, оплаты или клиента соответствующий кэш должен сбрасываться.
- Тяжёлые данные карточек следует предзагружать по намерению пользователя и получать компактными запросами без дублирующих обращений к базе.
- При прогретой инфраструктуре типовая операция чтения должна укладываться примерно в одну секунду; задержки выше этого значения требуют измерения и оптимизации.
- Проверка сохранённой сессии выполняется в фоне: уже подтверждённому пользователю не показывается полноэкранная заглушка при каждом обновлении страницы. API остаётся единственным источником проверки прав.

## Пользователи и роли

Текущие внутренние роли CRM:

| Роль | Системный код | Доступ |
| --- | --- | --- |
| Владелец/основатель | `owner_founder` | Полный доступ к любым карточкам сотрудников и клиентов, всем записям, финансам, зарплате, аналитике, справочникам, настройкам и любой другой информации системы. |
| SMM-менеджер | `smm_manager` | Только главная страница CRM и только специально разрешённые для SMM виджеты дашборда. Состав виджетов будет настроен позднее. |
| Владелец/сооснователь | `owner_cofounder` | Такой же полный доступ, как у владельца/основателя, при сохранении отдельной роли и авторства действий в аудите. |
| Администратор салона | `salon_admin` | Список и карточки клиентов с правом создавать и редактировать клиента; список и карточки записей с согласованными операционными действиями; список и просмотр услуг; собственная кассовая смена. |

- Термин `owner` в остальных требованиях означает обе полноправные роли: `owner_founder` и `owner_cofounder`.
- Администратор может создавать, подтверждать, переносить, отменять и финансово закрывать записи в рамках уже описанных сценариев. Редактирование каталога услуг ему пока не предоставляется.
- Администратор не имеет доступа к карточкам сотрудников, зарплате, зарплатным настройкам, оргструктуре, системным справочникам, глобальным настройкам и полной аналитике, если это не будет отдельно разрешено позднее.
- SMM-менеджер не получает доступ к API клиентов, записей, сотрудников, зарплаты, кассовых смен, справочников и настроек. Дашборд SMM использует отдельный ограниченный API-контракт без перехода к исходным карточкам.
- Скрытие пункта меню не считается защитой: ограничения применяются на маршрутах, API, отдельных действиях и полях ответа по принципу запрета по умолчанию.
- Изменение роли сотрудника, вход в систему и чувствительные действия сохраняются в журнале аудита.
- Client остаётся внешним пользователем клиентского сайта/кабинета, а не внутренней ролью CRM: он видит только свои записи, профиль, историю визитов и публичный статус лояльности.
- Отдельная внутренняя роль мастера пока не активна. На текущем этапе единственный мастер работает под ролью владельца/основателя; роль мастера с доступом только к собственным записям будет добавлена при найме мастеров.

## Клиентская запись

- Клиент может записаться без регистрации.
- Минимальные данные для записи: телефон и Telegram nickname.
- Дополнительные данные клиента: ФИО, email, WhatsApp, аллергии, заметки, фото ногтей.
- Клиент может выбрать мастера.
- Система должна показывать последнего мастера клиента, но позволять выбрать другого.
- На старте мастер один, но модель данных и интерфейс должны поддерживать несколько мастеров.
- Возможность записать несколько услуг в один визит не нужна в MVP, но должна быть учтена в архитектуре.

## Модерация записи

- Ручная модерация обязательна.
- Новая запись сначала попадает в статус ожидания подтверждения.
- Администратор подтверждает или отменяет запись вручную.
- За день до записей система уведомляет администратора в CRM и рабочий Telegram, что нужно подтвердить записи на завтра.
- Если клиент не подтвердил запись, администратор должен связаться с ним вручную: позвонить, написать в Telegram или WhatsApp.

## Источник и автор записи

- Для каждой записи обязательно сохраняется источник создания.
- Запись, созданная клиентом через публичный сайт, клиентский кабинет, Telegram Mini App или другой онлайн-канал, имеет источник `Online`.
- Запись, созданная сотрудником в CRM, имеет источник `Admin` и обязательную ссылку на аккаунт сотрудника, который её создал.
- В карточке и таблице записей источник отображается как `Online` либо как ФИО администратора-создателя.
- Авторство сохраняется исторически даже после увольнения или архивирования сотрудника.
- Источник и автор записи не меняются при переносе, подтверждении или смене мастера. Исправить ошибочно указанного автора может только владелец/основатель или владелец/сооснователь отдельным действием с обязательной причиной и записью в журнале аудита.
- Закрытая запись с источником `Online` не создаёт процент администратору. Закрытая запись, вручную созданная администратором, входит в расчёт его процента по действующей зарплатной политике.

## Отмена, перенос и неявка

- Клиент может отменить или перенести запись вплоть до времени приема.
- После неявки следующая запись клиента должна требовать предоплату.
- Отмена менее чем за 12 часов до приема считается поздней и также включает обязательную предоплату для следующей записи.
- При более ранней отмене или переносе обязательная предоплата не включается автоматически.
- Администратор может вручную включить или снять требование предоплаты с обязательным указанием причины.
- Предоплата в таком случае не возвращается.
- Онлайн-эквайринг будет позже, но уже сейчас нужен флаг клиента: requires_prepayment.
- CRM должна показывать причину, почему клиенту нужна предоплата.

## Закрытие записи и оплата

- Перевести запись в состояние `Закрыта` можно только с фиксацией результата визита и оплаты.
- Обязательные способы оплаты: онлайн-эквайринг, наличные, перевод по номеру телефона.
- Для оплаты сохраняются способ, сумма в минимальных денежных единицах, валюта, дата и время, сотрудник, принявший оплату, и при наличии идентификатор внешней транзакции.
- Архитектура поддерживает оплату одной записи несколькими способами. Сумма всех платежей должна совпадать с итоговой стоимостью записи, если отдельно не зафиксированы долг, скидка, возврат или корректировка с причиной.
- Наличные увеличивают расчётную сумму в кассе. Онлайн-эквайринг и перевод по номеру телефона учитываются как безналичные поступления и не увеличивают физическую кассу.
- После закрытия запись становится основанием для выручки и зарплатных процентов мастера и администратора. Отмена, неявка и незакрытая запись не создают такое начисление.
- Исправление оплаты или повторное открытие закрытой записи доступно только уполномоченной роли, требует причины и полностью журналируется. Связанные зарплатные и кассовые данные должны быть помечены для пересчёта или корректировки.

### Сценарий закрытия записи

- Роль: администратор салона, владелец/основатель или владелец/сооснователь; будущая роль мастера сможет передать результат визита без финансового закрытия.
- Цель: подтвердить оказанную услугу, зафиксировать фактическую оплату и передать запись в выручку и расчёт зарплаты.
- Шаги: проверить услугу и итоговую стоимость, выбрать один или несколько способов оплаты, указать суммы, проверить итог и закрыть запись.
- Ошибки: запись не закрывается без оплаты либо оформленного исключения; сумма платежей не может молча отличаться от итога; валюта платежа должна соответствовать расчёту; ошибка не меняет данные частично.
- Состояние данных: сохраняются снимок итоговой стоимости, платежи, источник и автор записи, закрывший сотрудник, время закрытия и аудит последующих исправлений.

## Единая карточка записи

Карточка записи должна быть основным рабочим пространством администратора и владельца. Она открывается из календаря поверх текущего контекста, занимает большую часть экрана на desktop и весь экран на мобильном устройстве. Пользователь не должен переходить по нескольким несвязанным разделам, чтобы подготовить, провести и закрыть один визит.

### Состав карточки

- Шапка: клиент, текущий статус, дата и время, мастер, источник и автор записи, итоговая стоимость, предупреждения об аллергиях и обязательной предоплате.
- Вкладка `Запись`: мастер, дата, свободное время, услуги, длительность, цены, процентная и фиксированная скидка, промокод, технический перерыв, подтверждение, состояния `пришёл`/`не пришёл`, напоминания, запрос отзыва, внутренний комментарий, цвет календарного события и вложения.
- Вкладка `Клиент`: основные контакты и быстрый переход к редактированию клиента; публичный статус лояльности; аллергии; приватные внутренние теги и заметки с соблюдением правил доступа.
- Вкладка `История записей`: дата и время, мастер, услуги, итог, статус, комментарий и переход к прошлой записи. Новая запись может быть создана повторением выбранного визита.
- Вкладка `Продажи и оплаты`: оказанные услуги и будущие дополнительные позиции, скидки, долг или корректировка, один или несколько платежей, сотрудник и время приёма каждого платежа.
- Вкладка `Статистика клиента`: последний визит, частота посещений, число записей, завершённые и отменённые визиты, неявки, общие траты, средний чек, клиентский баланс и бонусный баланс.
- Вкладка `Бонусы`: текущий баланс, начисление, списание и неизменяемый журнал операций с программой, суммой, датой, автором и связанной записью.
- Вкладка `Уведомления`: запланированные, отправленные и неуспешные уведомления, канал, время, шаблон и результат доставки.
- Вкладка `Изменения`: хронология создания, подтверждения, переноса, изменения услуги или цены, отмены, закрытия, повторного открытия и других чувствительных действий с автором и причиной.

### Действия и состояния

- Внизу карточки закреплены контекстные действия: отменить запись, повторить запись, сохранить изменения и перейти к финансовому закрытию.
- Изменение мастера, услуги, даты или времени всегда использует единый серверный расчёт свободных слотов и повторную проверку перед сохранением.
- Закрытие записи выполняется в этой же карточке без потери введённых данных и включает списание/начисление бонусов и распределение оплаты.
- После закрытия редактируемые поля блокируются. Повторное открытие доступно только уполномоченной роли, требует причины и не удаляет исходные платежи, бонусные операции и аудит.
- Состояния загрузки, пустых списков, ошибок и конфликтов одновременного редактирования должны быть явно показаны внутри карточки.
- Внутренние теги, служебные заметки и иные приватные характеристики клиента никогда не включаются в клиентский кабинет, Telegram Mini App или публичные API.

### Способы оплаты в карточке

- Карточка должна поддерживать разделение итоговой суммы между несколькими платежами.
- Требуемый перечень для проектирования: наличные, банковская карта/терминал, СБП, QR, перевод по номеру телефона, онлайн-эквайринг и `Другое` с обязательным комментарием.
- Для каждого платежа сохраняются сумма, валюта, способ, время, принявший сотрудник, внешний идентификатор при наличии и признак аннулирования/возврата.
- Бонусы не считаются способом оплаты: их списание уменьшает сумму к оплате и фиксируется отдельной операцией лояльности.

### Открытые продуктовые решения

- Подтвердить окончательную экономику бонусов: курс, автоматический процент начисления, максимальную долю списания и срок действия.
- Подтвердить, входят ли товары, сертификаты, абонементы и продажи в долг в первый этап карточки или добавляются после услуг и оплат.
- Подтвердить матрицу прав на скидку, корректировку цены, ручное начисление/списание бонусов и повторное открытие записи.
- Подтвердить, должны ли `QR` и `СБП` быть отдельными способами в отчётности или `QR` является интерфейсом оплаты через СБП.

## Склад материалов (базовый учёт)

- Справочник материалов: название, артикул, единица измерения (шт/мл/г), точка дозаказа, архивирование вместо удаления.
- За услугой можно закрепить расход материалов: сколько единиц каждого материала списывается за одно оказание услуги.
- Приход, инвентаризационная корректировка и списание порчи вносятся вручную с комментарием и автором; вся история — неизменяемый журнал движений (без стирания и перезаписи остатка).
- При финансовом закрытии записи материалы, закреплённые за услугой, списываются со склада автоматически. При переоткрытии записи списание возвращается отдельной корректирующей операцией, а не удалением истории.
- Остаток материала — сумма всех движений; отдельного хранимого поля «текущий остаток» нет, чтобы остаток не мог разойтись с историей.
- Материал считается дефицитным, когда остаток опускается до точки дозаказа или ниже; это лишь техническая база — уведомления и автозаказ не входят в текущий объём.
- Точный учёт расхода по граммам с себестоимостью (уровень специализированных инструментов для окрашивания волос) сознательно не реализуется — избыточен для ногтевого сервиса.

## Расписание

- Между записями по умолчанию нет обязательного буфера.
- Должна быть возможность вручную добавить перерыв или блокировку времени.
- Нужны обеды, выходные, отпуск, исключения и индивидуальный график мастера.
- График мастеров должен быть составлен за 1,5 недели до наступления месяца.
- Система должна уметь напоминать владельцу/админу о необходимости подготовить график.
- Для первого макета конкретные рабочие дни и часы не фиксируются.
- Напоминание подготовить график отправляется за 11 дней до начала месяца в 10:00 по часовому поясу филиала.
- Запись доступна на 60 дней вперед, минимум за 2 часа до приема, с шагом начала слота 30 минут.
- При любом сценарии создания записи сначала выбираются мастер, услуга и дата, после чего система показывает календарь и только фактически свободные окна.
- Один backend-расчёт доступности используется CRM, публичной онлайн-записью, клиентским кабинетом и Telegram Mini App, чтобы разные каналы не показывали противоречащие друг другу слоты.
- Свободное окно учитывает рабочие часы мастера, дополнительные часы, отпуск, выходные, обеды и другие блокировки, активные записи, длительность услуги и её технический буфер.
- Выбранный слот повторно проверяется сервером в момент сохранения. Занятый, устаревший или вручную подменённый интервал отклоняется без создания записи.
- При переносе записи используется тот же календарь доступности: можно изменить мастера, услугу и дату, а исходная переносимая запись исключается из расчёта занятости.
- Если график мастера на выбранную дату не составлен, свободные окна отсутствуют; CRM предлагает выбрать другую дату или перейти к настройке графика.

## Лист ожидания

- Администратор может добавить клиента в лист ожидания с указанием услуги, желаемого мастера (или «любой») и желаемого периода дат.
- Запись в листе ожидания имеет статусы: ждёт, предупредили, записан, отменено.
- Лист ожидания не бронирует слот и не создаёт запись автоматически: при освободившемся окне администратор вручную связывается с клиентом и оформляет запись обычным способом.

## Ограничения услуг

На старте нет услуг, которые нельзя ставить подряд.

Примеры будущих ограничений:

- после очень длинной услуги нужен технический перерыв;
- сложный дизайн нельзя ставить в короткий слот;
- услуга требует дополнительной подготовки рабочего места;
- после услуги с агрессивными материалами нужен буфер на уборку/проветривание;
- услуга доступна только конкретному мастеру.

## Статусы клиента

Есть два разных типа статусов:

- Публичный статус лояльности: виден клиенту, используется в клиентском кабинете и мотивации.
- Внутренние статусы/метки: создаются админом, видны только внутри CRM.

Критическое правило: внутренние статусы и метки клиента никогда не должны отображаться клиенту, передаваться в клиентский кабинет, Telegram Mini App или публичные API.

## Внутренние теги и заметки клиента

- В карточке клиента показывается облако доступных внутренних тегов с поиском, автодополнением и множественным выбором.
- Теги повторно используются между карточками клиентов. Примеры: `скандальный`, `требовательный`, `доебистый`, `лапочка` и другие теги, созданные владельцем или уполномоченным администратором.
- Выбранные теги визуально отличаются от невыбранных; тег можно назначить и снять без удаления из общего справочника.
- Для назначения и снятия тега сохраняются автор, дата и история изменения.
- Свободное текстовое поле внутренних заметок сохраняется отдельно: облако тегов дополняет заметки, но не заменяет их.
- Создание, переименование, объединение и архивирование тегов ограничивается правами роли. Архивный тег сохраняется в истории, но не предлагается для новых назначений.
- Внутренние теги доступны только в защищённом CRM API сотрудникам с соответствующими правами. Они не включаются в ответы клиентского API даже при запросе собственной карточки клиентом.

## Аллергии клиента

- При создании клиента в CRM и при самостоятельной регистрации/записи клиенту показывается отдельное облако распространённых аллергенов с поиском и множественным выбором.
- Начальный справочник должен включать относящиеся к маникюрным услугам группы: акрилаты и метакрилаты, включая HEMA; клеевые составы; латекс; никель; отдушки; консерванты; антисептики и дезинфицирующие составы. Медицинские формулировки и стартовый список отдельно проверяются перед публичным запуском.
- Пользователь может выбрать `Другой аллерген` и добавить собственное текстовое значение.
- Собственное значение сохраняется в карточке клиента, но не попадает автоматически в общий справочник. Владелец или администратор салона может позднее сопоставить его с существующим аллергеном; добавлять значения в общий справочник могут только роли владельцев.
- Состояния `Нет известных аллергий` и `Не указано` различаются. `Нет известных аллергий` нельзя выбрать одновременно с конкретными аллергенами.
- Для аллергена можно сохранить описание реакции, степень важности, комментарий, источник сведений и дату последнего уточнения.
- Аллергии отображаются заметным предупреждением в карточке клиента и в связанной записи для администратора и назначенного мастера.
- Клиент может просматривать, добавлять, исправлять и удалять собственные сведения об аллергиях. Внутренние клиентские теги при этом ему не показываются.
- Данные об аллергиях рассматриваются как чувствительные персональные данные: доступ ограничивается ролями, а изменения журналируются.

### Сценарий заполнения тегов и аллергий

- Роль: обе роли владельцев или администратор салона при создании карточки в CRM либо client при самостоятельной регистрации в части аллергий.
- Цель: быстро выбрать повторно используемые характеристики и зафиксировать важные ограничения для безопасного оказания услуги.
- Шаги: найти и выбрать внутренние теги в CRM, выбрать известные аллергены, при необходимости добавить собственный аллерген и описание реакции, сохранить карточку.
- Ошибки: нельзя одновременно сохранить `Нет известных аллергий` и конкретный аллерген; дубликаты нормализуются; внутренние теги отклоняются публичным API и никогда не возвращаются клиенту.
- Состояние данных: внутренние теги имеют историю назначений, аллергены хранят источник и дату уточнения, свободные заметки остаются отдельным полем.

## Гостевые предпочтения (welcome-набор, напитки, ароматы)

Отдельная сущность от аллергий: не про безопасность услуги, а про персонализацию приёма клиента — какой кофе/чай предложить, какое молоко, какие конфеты, состав welcome-набора, какие ароматы. Цель — чтобы администратор мог заранее подготовиться к визиту конкретного гостя.

Критическое правило (явно подтверждено владельцем): это внутренняя информация, полностью аналогичная приватным внутренним меткам клиента. Клиент никогда не должен её видеть, вводить или редактировать — ни в личном кабинете, ни в Telegram Mini App, ни в любом публичном API. Заполняется и читается только персоналом в CRM, так же как внутренние теги и заметки (см. раздел «Внутренние теги и заметки клиента»).

Статус: осознанно не структурировано — решено пока не проектировать фиксированные справочники по категориям. Не начато.

## Кассовая смена администратора

- Администратор должен иметь возможность открыть и закрыть свою операционную кассовую смену; состояние текущей смены заметно в CRM.
- При открытии смены фиксируются сотрудник, филиал/организация, касса, дата и время и фактический остаток наличных на начало смены.
- Закрытие смены формирует и сохраняет сводный отчёт за точный период смены.
- Отчёт содержит: сотрудника и период смены, количество и сумму закрытых записей, общую выручку, разбивку по способам оплаты, дебет/приход, кредит/расход, возвраты, внесения, изъятия и корректировки.
- Отдельно показываются расчётная сумма наличных в кассе, введённая администратором фактическая сумма, ожидаемая общая сумма поступлений за смену и расхождение.
- Расчётная касса определяется как остаток на начало плюс наличные оплаты и внесения минус наличные возвраты, расходы и изъятия. Онлайн-эквайринг и переводы по номеру телефона в физическую кассу не включаются.
- Каждая ручная операция дебета/кредита содержит тип, сумму, валюту, комментарий, автора и время. Для расходов и корректировок причина обязательна.
- Перед закрытием система показывает незакрытые записи и неполные оплаты за период. Закрытие при наличии расхождения или проблемной записи требует обязательного комментария и, в зависимости от будущей матрицы прав, подтверждения одной из ролей владельца.
- После закрытия отчёт и исходные показатели смены блокируются от обычного редактирования. Исправление выполняется владельцем/основателем или владельцем/сооснователем отдельной корректировкой с сохранением исходных значений и аудита.
- Суммы разных валют показываются отдельными блоками и никогда не складываются в единый итог. Для текущей московской точки основной валютой является RUB.
- Обе роли владельцев видят все смены, могут фильтровать их по сотруднику, дате, организации, подразделению и состоянию, а также открывать расшифровку до конкретных записей и кассовых операций.
- Сводный отчёт смены является внутренним управленческим документом CRM и не заменяет официальный кассовый чек, фискальный документ или бухгалтерскую отчётность.

### Сценарий закрытия смены

- Роль: администратор салона; контролирующая роль — владелец/основатель или владелец/сооснователь.
- Цель: сверить выручку и физическую кассу, зафиксировать расхождения и завершить рабочий период администратора.
- Шаги: открыть сводку смены, проверить закрытые записи и способы оплаты, внести фактическую сумму наличных, проверить дебет/кредит и расхождение, добавить комментарий при необходимости и закрыть смену.
- Ошибки: нельзя закрыть уже закрытую смену, объединить разные валюты, оставить необъяснённое расхождение или потерять незавершённые платежи; API возвращает ошибку без частичного закрытия.
- Состояние данных: отчёт хранит неизменяемый снимок расчётных и фактических сумм, автора закрытия, время, комментарий и историю корректировок владельцев.

## Навигация CRM

- Все существующие разделы CRM сохраняются: обзор, записи, клиенты, услуги и расписание.
- В левой колонке добавляется раздел `Персонал` с подвкладками `Сотрудники`, `Структура подразделений` и `Руководители`.
- В левой колонке добавляется раздел `Справочники` с отдельными справочниками, перечисленными ниже.
- В левой колонке добавляется раздел `Зарплата` с основной таблицей и подвкладкой `Настройки зарплаты`.
- Группы с подвкладками могут сворачиваться и раскрываться; текущий раздел и подвкладка должны иметь однозначное активное состояние.
- Доступность разделов и отдельных действий определяется ролью. Кадровые дела, зарплата и зарплатные настройки доступны только владельцу/основателю и владельцу/сооснователю, пока отдельно не согласована более детальная матрица прав.

## Персонал и организационная структура

### Персонал: сотрудники

Подвкладка `Сотрудники` представляет собой таблицу со столбцами:

- ФИО;
- почта;
- основная должность;
- основное подразделение;
- основная организация;
- город;
- страна.

Строка таблицы открывает карточку сотрудника. Основная должность выбирается только из справочника должностей, основное подразделение — из оргструктуры, основная организация — из справочника организаций, город и страна — из соответствующих справочников. Архивирование сотрудника не должно удалять его прошлые записи, начисления, выплаты и назначения руководителем.

### Персонал: структура подразделений

- Подвкладка должна позволять выстроить иерархическую оргструктуру компании.
- Оргструктура поддерживает организации, группы, подразделения, отделы и другие настраиваемые типы организационных объектов.
- Для объекта хранятся название, тип, родительский объект, организация, город/страна, состояние и период действия.
- Должны поддерживаться создание, переименование, перемещение внутри дерева и архивирование объектов.
- Система не допускает циклическую структуру и не удаляет используемые объекты без сохранения истории.

### Персонал: руководители

Подвкладка `Руководители` представляет собой таблицу со столбцами:

- ФИО руководителя;
- тип объекта руководства: группа, подразделение, отдел и другие типы;
- название объекта руководства;
- тип руководителя: ресурсный пул, администратор подразделения, непосредственный руководитель и другие типы.

Руководитель выбирается из сотрудников, объект руководства — из оргструктуры, тип руководителя — из справочника типов руководства. Один объект может иметь нескольких руководителей разных типов. Для назначения сохраняются даты начала и окончания действия, чтобы кадровая история не терялась.

## Справочники

Обязательные справочники:

- должности;
- города;
- страны;
- организации;
- типы организационных объектов;
- типы руководителей;
- виды занятости и кадровые статусы;
- виды ручных начислений, премий, удержаний и доплат;
- способы выплаты зарплаты;
- способы оплаты клиентов;
- кассы и типы кассовых операций;
- внутренние теги клиентов;
- распространённые аллергены.

Город связывается со страной. Записи справочников, которые уже используются в связанных данных сотрудников, клиентов, оргструктуры или зарплаты, архивируются вместо физического удаления. Изменения справочников должны сохранять автора и время изменения.

## Зарплата

- Раздел зарплаты и все зарплатные данные доступны только владельцу/основателю и владельцу/сооснователю.
- Основной экран зарплаты содержит выбор расчётного периода и табличное представление.
- В таблице показываются ФИО сотрудника, должность сотрудника, сумма к начислению за период и флаг `Начислено` со значением да/нет.
- Справа в каждой строке располагаются действия по расчёту и кнопка `Сформировать PDF` для расчётного листа.
- Формат расчётного листа будет предоставлен владельцем позже; до этого PDF-функция проектируется как отдельный шаблонизируемый экспорт.
- Сумма в таблице открывает детализацию зарплаты сотрудника за период, включая происхождение суммы по каждой записи.
- Флаг `Начислено` является упрощённым отображением факта начисления; в деталях продолжают использоваться состояния: не начислено, начислено, выплачено частично, выплачено, требуется корректировка.
- Для мастера базовое начисление составляет 46% от стоимости завершённых записей этого мастера.
- Для администратора базовое начисление составляет 13% от стоимости завершённых записей, созданных вручную под его аккаунтом.
- Для администратора поддерживаются фиксированная часть, доплата за уборку, премии и другие ручные начисления.
- Поддерживаются удержания и корректировки с обязательным текстовым основанием.
- Каждая процентная сумма должна иметь расшифровку до исходной записи: клиент, услуга, стоимость, ставка и сумма начисления.
- Начисление выполняется владельцем вручную и фиксирует снимок условий, записей и итогов за месяц.
- До первой выплаты начисление можно пересчитать. После первой выплаты условия и автоматическая часть расчёта периода блокируются от изменения.
- Выплаты фиксируются отдельно с суммой, датой и способом. Поддерживаются частичные выплаты.
- Состояния расчёта: не начислено, начислено, выплачено частично, выплачено, требуется корректировка.
- Не начисленный и начисленный расчёт показывается жёлтым, частично выплаченный — синим, выплаченный — зелёным, требующий корректировки — красным.
- Суммы хранятся в минимальных денежных единицах вместе с валютой. Записи разных валют не объединяются в один расчёт.
- Для Москвы текущая зарплатная политика использует RUB. Для будущих стран и филиалов задаются отдельные правила, валюта и дата начала действия.

### Настройки зарплаты

- Подвкладка `Настройки зарплаты` содержит таблицу соответствий между должностью и процентом с продаж.
- Должность выбирается только из справочника должностей; свободный текст не используется.
- Должность в зарплатной настройке сопоставляется с основной должностью из карточки сотрудника.
- Стартовые настройки: мастер — 46%, администратор — 13%.
- Помимо процента настройка хранит правила базы расчёта: для мастера — завершённые записи этого мастера, для администратора — завершённые записи, созданные вручную под его аккаунтом.
- Для изменения политики сохраняются дата начала действия и история предыдущих значений. Изменение процента не должно пересчитывать уже начисленные и тем более выплаченные периоды.
- Архитектура настроек должна позволять в будущем задавать разные политики по организации, подразделению, стране и валюте.

### Сценарий начисления зарплаты

- Роль: владелец/основатель или владелец/сооснователь.
- Цель: проверить происхождение каждой суммы, начислить зарплату сотруднику и отметить фактическую выплату.
- Шаги: выбрать сотрудника и месяц, проверить условия и записи, добавить премии/удержания, начислить итог, затем зарегистрировать одну или несколько выплат.
- Ошибки: нельзя включить запись другой валюты, выплатить больше остатка, изменить условия или пересчитать автоматическую часть после первой выплаты; API возвращает явную ошибку без изменения данных.
- Состояние данных: до начисления показывается динамический предварительный расчёт; после начисления хранится неизменяемый снимок; выплаты и ручные корректировки имеют отдельную историю и автора действия.

### В карточке записи

Модальное окно записи (`apps/web/app/appointments/page.tsx`, вкладка
«Запись») с 2026-10-29 переверстано как точная структурная копия DIKIDI
«Изменение записи»: ряд Мастер/Дата/Время (всегда редактируемый, без
отдельного тоггла «Перенести»), строка(и) услуг с живым пересчётом
Скидка-%/Скидка-Σ/Итого и строкой общих итогов, блок клиента с
«Подтвердил»/«Пришёл»/«Не пришёл», ссылки «История записей»/«История
уведомлений»/«История изменений» на соответствующие вкладки, комментарий +
цвет записи, футер Отменить/Повторить/Оформить продажу/Сохранить. Плотность
и палитра цветных меток подогнаны под измеренные пиксельные значения из
референса DIKIDI (не наша обычная палитра статусов).

Оплата вынесена из основной карточки в два отдельных модальных окна, как в
DIKIDI: «Продажа товаров и услуг» (сводка по услугам/итогам, пометки,
цвет записи → кнопка «Перейти к оплате») и «Оплата товаров и услуг» (сетка
иконок способа оплаты, сумма, бонусы, строка Итого/Оплачено/Долг). Кнопки
«Оформить продажу» в футере и «Пришёл» в блоке клиента открывают эту
цепочку. Backend не менялся — оба окна используют существующий
`POST /v1/admin/appointments/:id/close`.

Добавление услуги к записи (кнопка «+» в строке услуг) — текстовый ввод с
автокомплитом по первым буквам названия (до 8 совпадений), а не выпадающий
список: у одного мастера может быть 100+ услуг.

Форма «Новая запись»: поле «Клиент» имеет переключатель «+ новый клиент» —
раскрывает поля Имя/Телефон и создаёт клиента через существующий
`POST /v1/admin/clients` перед созданием записи, без ухода из формы. Доступно
и из пустого состояния «Сначала добавьте клиента».

- ✅ Несколько услуг в одной записи — реализовано полноценно (не заглушка):
  новая таблица `AppointmentService` хранит дополнительные строки услуг,
  каждая со своей скидкой; `Appointment.priceMinor`/`endsAt` всегда равны
  сумме по всем строкам. Эндпоинты `POST/PATCH/DELETE
  /v1/admin/appointments/:id/services[/:lineId]` добавляют/редактируют/

- ✅ Скидка % / скидка суммой и промокод прямо в карточке записи — сделано,

  /v1/admin/appointments/:id/pricing` (основная услуга) и `PATCH

- ✅ «Шаблон недели» — прежний редактор повторяющегося недельного графика +

- ✅ Выделение ячеек в месячном гриде — клик по ячейке переключает её

  цвета сверены пипеткой с референсом DIKIDI. Обе кнопки применяются
  батчем ко всем выбранным ячейкам сразу через `PUT
  /v1/admin/schedule/day` (см. ниже), затем сбрасывают выбор.
- ✅ Попап «Рабочее время» (`apps/web/app/ui/working-hours-popover.tsx`) —
  отдельный плавающий компонент (белая карточка с крестиком закрытия),
  используется только на `/appointments` — клик по ссылке с часами под
  именем мастера в шапке дневного грида, как в DIKIDI «Журнал записей».
  Начало/конец, чекбокс «С перерывом», ссылка «сделать день нерабочим»,
  кнопка «Готово». На `/schedule` этот плавающий попап не используется —
  там выбор ячеек правится через докнутый редактор в сайдбаре (см. выше),
  это два разных UI-паттерна DIKIDI для двух разных экранов.
  Оба сохраняют через новый `PUT /v1/admin/schedule/day` — задаёт рабочее
  время на один конкретный день для одного мастера (0, 1 или 2
  интервала), не трогая недельный шаблон. Реализовано поверх существующих
  `ScheduleException`: один `isBookable:false` на весь день + 0–2
  `isBookable:true` поверх него. Отказывает (409), если на этот день уже
  заходит многодневное исключение (отпуск) — такие по-прежнему правятся

- ✅ Защита от «потерянных» записей: `PUT /v1/admin/schedule/day` отказывает

  одну активную запись (draft/ожидает подтверждения/подтверждена) вне всех
  новых интервалов — нельзя закрыть день, если на него уже есть записи, их

  сайдбаре `/schedule`, и в попапе на `/appointments`.
- ⏳ «Отобразить пометки о записях в графике» — чекбокс показан, но
  неактивен: нужен отдельный запрос количества записей по дням, не сделан.
- Попутно исправлена `resolveWorkingRanges`: она не вычитала
  `isBookable:false` исключения, поэтому полностью закрытый день
  (отпуск/выходной) в `day-overview` выглядел как обычный рабочий день.

  Удалены, Штрафники (была хотя бы одна запись со статусом `no_show`).
  Клик по категории — фильтр списка (`GET /v1/admin/clients?category=...`),
  повторный клик снимает фильтр. Вся логика вынесена в чистую функцию
  `categorizeClient()` (`apps/api/src/clients.ts`), покрыта юнит-тестами.
- ✅ Чёрный список клиента — поле `Client.isBlocked`, чекбокс «Клиент
  заблокирован» в карточке. Блокирует только самостоятельную онлайн-запись
  (`POST /v1/appointments` отвечает 403 `client_blocked`), запись из CRM
  администратором по-прежнему доступна.
- ✅ Удаление клиента — мягкое (`Client.deletedAt`), через `DELETE
  /v1/admin/clients/:id` (массово — из «...» в тулбаре по отмеченным
  чекбоксами) и `POST /v1/admin/clients/:id/restore`. Удалённые скрыты из
  обычного списка, из `/v1/admin/booking-options` (выбор клиента при ручной
  записи) и из подсчёта остальных категорий; видны только при выборе
  категории «Удалены», где вместо редактирования — кнопка «Восстановить».
- ✅ «Скидка, %» — `Client.discountPercent`, стандартная персональная скидка
  клиента (0–100), отдельно от разовых скидок/промокода на конкретной
  записи. Поле в карточке клиента.
- ✅ Массовое начисление бонусов — отметить клиентов чекбоксами → «Начислить
  бонусы» → баллы и причина применяются всем отмеченным разом (цикл по
  существующему `POST /v1/admin/clients/:id/loyalty-transactions`, без
  нового бэкенда).
- ✅ «Поиск по специалистам» — фильтр `GET /v1/admin/clients?staffId=...`:
  только клиенты, у которых есть хотя бы одна запись к этому мастеру.
- ⏳ «Карта» (поиск по номеру карты лояльности) — поле в тулбаре есть, но
  неактивно: в модели клиента нет понятия номера карты, это отдельная
  функциональность (физические/цифровые карты), не входила в эту задачу.
- ⏳ «Группы» — раздел и выпадающий список показаны («Все группы»), но
  группы клиентов как сущность не реализованы: нужна отдельная модель
  (создание/редактирование групп, назначение клиентов) — самостоятельная
  задача, не одна из восьми аналитических категорий.

### В карточке клиента

- Баланс клиента (предоплата/депозит) — отдельная сущность от бонусов.
- Бонусный счёт как полноценный леджер: начисление/списание вручную,
  история операций с типом/программой/суммой/датой (сейчас бонусы учтены
  только как два числа при закрытии записи — `bonusRedemptionPoints`/
  `bonusBalancePoints`, без истории операций и ручного начисления).
- Вкладка "Статистика": последняя запись, посещаемость (визитов/месяц),
  всего записей, потрачено, средний чек — агрегаты, которые можно посчитать
  из уже существующих данных (Appointment + Payment), не хватает только
  отдельного вычисляемого представления.
- Источник клиента (lead source) как поле карточки.
- Продажа товаров/сертификатов клиенту, отдельно от записи на услугу, с учётом
  долга ("Продажи" таб: количество/оплачено/долг) — требует нового понятия
  "товар на продажу", отличного от текущего складского учёта материалов
  (`Склад материалов` — это расход материалов на услугу, не розница).
- Абонементы (предоплаченные пакеты услуг/посещений) — отдельная сущность,
  которой нет вообще; затрагивает запись (списание визита с абонемента вместо
  оплаты), клиента (баланс абонементов) и аналитику.
- Журнал звонков — интеграция с телефонией, вероятно не актуально без
  подключённой IP-телефонии; низкий приоритет.
- Согласия клиента как отдельная вкладка с историей — частично уже заложено
  в разделе "Платежи и юридические документы" (согласие на рассылки,
  возможность отзыва), не хватает только UI-истории согласий по датам.

### Виджеты

- "Финансы за сегодня" на календаре (нал/безнал за день) — считается из уже
  существующей модели `Payment`, не хватает только виджета.
